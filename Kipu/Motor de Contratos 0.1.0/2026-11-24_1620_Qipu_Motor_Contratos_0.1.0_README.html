Una definición de campo no crea un dato. Una afirmación reconocida sí constituye lo que su contrato permite. No necesitamos preparar una tabla física ni emitir un CREATE separado para cada producto.

K es el contrato reconocido, V los espacios y celdas, H la historia derivada de acciones. El génesis reconoce exclusivamente el perfil QIPU-META-1; la instancia comienza sin tipos, tablas ni productos. El editor produce definiciones; la autoridad las reconoce antes de hechos que dependen de ellas. El contrato precede lógicamente al dato, aun si ambos comparten la misma trayectoria.

02 · Metacontrato y evolución

La gramática de bootstrap es código confiable y finito. Sus instancias son datos. Una definición puede añadir tipos, parámetros y acciones en un solo lote atómico. El mismo nombre puede reafirmarse con exactamente la misma definición, pero una redefinición incompatible es rechazada. Para una acción nueva use una identidad nueva (Venta-v2). No se reinterpreta la historia ni se ejecuta código recibido.

r₀Génesis
r₁Contrato: Producto, Nombre
r₂SKU-A, Camisa
r₃Contrato: Peso
r₄SKU-A, Peso=250

La identidad del contrato de acción permanece estable para solicitudes offline. Una definición provisional puede ser rechazada; las solicitudes dependientes se mantienen históricamente y se recalculan sobre el contrato reconocido. Una solicitud estructuralmente válida puede estar semánticamente bloqueada.

Campo

Los dominios disponibles son text, natural y boolean. ADD/SUB solo se admiten sobre naturales previamente asignados. SET puede constituir la identidad únicamente si el campo es constitutive. Una acción siempre es referencial: no crea identidades por accidente. Las operaciones son de orden explícito. No hay campos obligatorios globales ni forma fija de producto.

05 · Composición de tratamientos

Una acción define entradas ordenadas, efectos y una medida opcional. Cada efecto liga una entrada a un parámetro y un tratamiento. El intérprete no necesita saber qué significa venta: valida dominios, aplica efectos a un candidato y consolida solo si todo es válido.

{"name":"Venta-v1","table":"Producto","inputs":[
 {"name":"cantidad","domain":"natural","positive":true},
 {"name":"precio","domain":"natural","positive":false}],
 "effects":[{"parameter":"Stock","operation":"SUB","input":"cantidad"}],
 "measure":["cantidad","precio"]}
S′[i] = S[i] − Σ(qⱼ : iⱼ=i) Medida = Σ qⱼ × pⱼ ∀ i: S′[i] ≥ 0

Una sola acción puede afectar varias entidades y varios parámetros de la misma tabla. Si una línea falla, el lote entero falla. El orden de líneas y efectos es semántico. Se deriva una historia de acciones con valores originales y medida; no se registran adicionalmente los descuentos. PHP usa copia por valor y JS structuredClone para estados candidatos. Este perfil no permite transformaciones arbitrarias ni ejecución de código de usuario.

06 · Comercio es una plantilla

Registrar Nombre puede constituir SKU-A. Asignar Stock a 20 no equivale a recibir 20 unidades. Venta de 5 reduce a 15, otra asignación de 18 sustituye a 18. Una nueva afirmación del nombre conserva el inventario. El precio pactado se incluye en las entradas de la venta. Precio autorizado y vigencia del conteo absoluto siguen siendo decisiones de la autoridad, no una regla de este perfil.

SET₁₈(SUB₅(20)) = 18 SUB₅(SET₁₈(20)) = 13

Una acción Entrada-v1 con ADD puede crearse visualmente sin tocar Motor.php ni motor.js. Otro tipo Cliente con Nombre y Activo también se interpreta sin tocar código. No hay clase Producto, ni switch de venta en el motor.

08 · Localidades, solicitudes, autoridad

L existe sin red. N registra localidades por primera aparición. Q es proyección de T101 de L, no una segunda cola. T100/T102 permanecen locales. Se preparan Q y R vacíos antes de anexar localidad a N. Para n localidades, 2n+2 archivos lógicos remotos. La autoridad toma Qⱼ[|Rⱼ|], verifica contrato y estado vigentes y decide. La aceptación escribe C antes de R=1; rechazo escribe solamente R=0. La procedencia (localidad, índice Q) hace recuperable la interrupción entre ambos archivos. Solicitudes idénticas en posiciones distintas son hechos distintos.

0 ≤ |Rⱼ| ≤ |Qⱼ| ≤ |Proyección(Lⱼ)| Cⱼ ≼ C Bᵢ = 128dᵢ + (i mod 128)

10 · Tres conocimientos; un orden canónico

PrivadoContratos y hechos T102 propios. Nunca se publican automáticamente.
CanónicoDerivado exacto del prefijo C adquirido.
OperativoCanónico más solicitudes propias aún compatibles, no rechazadas ni incorporadas.

Si R=1 llega antes de C, se conserva el efecto provisional compatible. Si C llega antes de R, la procedencia elimina la repetición del efecto. Si R=0, se retira el efecto provisional; no se borra la historia. Una contradicción R=0 con origen canónico presente bloquea incorporación. Si un contrato se rechaza, las acciones dependientes pueden quedar en conflicto. Al mismo corte, ambos intérpretes correctos deben dar el mismo D.

12 · Pruebas ejecutadas y evidencia
45/45 HTTP + JavaScript en servidor PHP integrado (4 workers); 45/45 en Apache con mod_php; 6/6 recuperación PHP; 15/15 PAO original (incluye 64 escritores). Total 111 comprobaciones ejecutadas, 45 repetidas en dos entornos, no 111 propiedades independientes. En cada ejecución HTTP se compararon los 22 cortes con PHP CLI y se regeneró el marco binario exacto. Ejemplo de 4.902 bytes. Las tres ventas concurrentes de 9,8,7 sobre 20 producen dos aceptaciones y un rechazo. El resultado final después de acciones adicionales es stock A=16 y cinco acciones derivadas.
También se verificaron evolución aditiva, redefinición incompatible atómica, Cliente/Activo=false, posiciones estables, venta multilínea, procedencia y convergencia de las tres localidades. Las interrupciones son simuladas; no son ensayos eléctricos. Chromium devolvió ERR_BLOCKED_BY_ADMINISTRATOR para localhost, salida 77. Prueba de UI/IndexedDB lista pero no superada ni contabilizada. No se ejecutaron pruebas de millones de registros.

13 · Instalación, estructura y límites
php -S 127.0.0.1:8080 -t public
Abrir http://127.0.0.1:8080/. Activar plantilla Comercio en la UI; registrar en L; publicar; aceptar solicitudes en orden desde autoridad; adquirir C y R. El README no necesita servidor. Requiere PHP 8.1+ de 64 bits, filesystem POSIX local con flock/fsync y navegador moderno en localhost/HTTPS. No CDN, OAuth, Node ni Python para ejecutar. Las herramientas de prueba son optativas.

Experimental, sin autenticación. No desplegar el endpoint públicamente. El repositorio de código no equivale a un servicio operativo. La base qipu-motor-v01 y data-motor-v01 son independientes de versiones anteriores. No migrar ni reemplazar historias previas automáticamente.
Decisiones de este perfil: nombres contractuales ASCII e identidades UTF-8 acotadas a 200 bytes; naturales hasta 10⁹, medidas enteras seguras; flujo máximo 4 MiB. Son límites de laboratorio, no axiomas. No se han implementado UNSET, APPEND general, nulos, migraciones de dominio, acciones entre tablas, autorización por parámetro ni compilación K2P de hechos. El motor resuelve nombres por búsqueda y clona candidatos; IndexedDB conserva bloques completos por flujo. Estas optimizaciones quedan abiertas sin cambiar la semántica. No hay ejecución de código arbitrario dentro de contratos. Preservar las versiones antiguas es parte del método.
Referencias de diseño: Khipu Continuidad UI V2 PHP (21 nov), Qipu Continuidad 1.0, Qipu 2.1 + PAO 1.1, Comercio 1.0, Comercio Vectorial 0.1.0. El nuevo motor recupera el metacontrato de UI y lo extiende a reconocimiento de escritura.
