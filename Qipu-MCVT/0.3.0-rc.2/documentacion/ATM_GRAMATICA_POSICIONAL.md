# ATM — geometría y gramática posicional
25-nov-2026. Revisión conceptual de RC.2, no cambio de protocolo ni implementación.

## Evidencia del código
local/kernel.js, líneas 300–344: identity(t,id,create) constituye primero la tabla del tipo t si no existe y después una identidad en su vector de identidades. Una afirmación SET puede constituir un vector de parámetro. La celda se guarda con clave ['cell',ti,vi,i]. snapshot (384–406) recorre tablas, identidades y vectores; cada vector contiene manifestaciones por posición de identidad. servidor/Kernel.php, líneas 840–862, conserva la misma geometría. Una identidad puede registrarse explícitamente (ID) sin que existan vectores de parámetros; exige tipo declarado. Declarar un tipo no crea tabla. No confundir tipo de entidad (Producto, representado por una tabla al constituirse) e identidad de una instancia (SKU-A, posición dentro de la tabla).

local/atm.js: read usa [t,i,v] y [t,null,v] para consultar un vector, aunque el núcleo usa [t,v,i]. meta() mezcla tipos por orden de declaración con posiciones de tablas por orden de constitución, y devuelve objetos nominales. Los campos se ordenan por vector constituido, con los no constituidos al final. translate convierte las posiciones en nombres para generar acontecimientos nominales T120/T101. servidor/ATM.php reproduce la interfaz híbrida. Esta es una adaptación posterior, no la geometría original. Las pruebas de RC.2 verifican equivalencia con esa adaptación, no una API estrictamente posicional.

## Definición
La API de una trayectoria en un corte es el lenguaje de preguntas que permite conocer su metacontrato y metaestructura y, mediante ese conocimiento, referir sus manifestaciones y formular transformaciones admisibles. La gramática del intérprete permanece; las posibilidades y coordenadas reconocidas evolucionan. La forma fundamental de expresión son listas ordenadas de posiciones. Los nombres son manifestaciones de identidad, no etiquetas redundantes en cada solicitud. JSON de listas es una serialización posible; JSON nominal es proyección de conveniencia. No se genera código ni se introduce otra fuente de verdad.

## Geometrías distintas
C: metacontrato (posibilidades declaradas). Propuesta de representación C=[tipos,campos,acciones], cada familia ordenada por declaración, con referencias cruzadas posicionales. M: metaestructura constituida, una secuencia de tablas por primera aparición. Propuesta M[t]=[tipoDeclarado, I_t, V_t], I_t lista de identidades por primera aparición, V_t lista de referencias a declaraciones de campo por orden de primera manifestación. El índice declarado de un tipo/campo no tiene por qué coincidir con t/v. El contrato contiene los nombres, dominios y leyes; no repetirlos en M si una referencia basta. D[t][v][i] es la manifestación (parcial); un vector es una secuencia indexada por las mismas identidades I_t. Ausencia no equivale a 0 o false. Se puede representar un vector parcial por pares [i,x], o por lista densa con huecos null según perfil actual (null no es valor). No compactar eliminando huecos sin conservar sus posiciones.

## Propuesta para discusión: gramática por prefijo
Una raíz de conocimiento puede organizarse como [C,M,D]. En una interfaz vinculada a una trayectoria, [0] selecciona C, [1] selecciona M y [2] selecciona D. La ruta se prolonga solo en la medida necesaria. Ejemplos:
[0,0] tipos declarados; [0,1] campos; [0,2] acciones.
[1,t,0] referencia a tipo declarado; [1,t,1] identidades I_t; [1,t,1,i] identidad; [1,t,2] referencias de vectores V_t; [1,t,2,v] declaración asociada al vector.
[2,t,v] vector de manifestaciones; [2,t,v,i] una manifestación.
Con D ya fijado, [t,v,i] basta. Con tabla fijada, [v,i] basta. El orden de recorrido coincide con el núcleo. La fila de una identidad se deriva tomando D[t,v,i] para cada v; no es una segunda geometría. [] como selección conceptual de raíz no obliga a transferir todos sus contenidos: puede usarse un contexto de descubrimiento separado o referencias a ramas; el contrato de transporte queda por decidir. Los selectores 0/1/2 y subramas son propuesta, no sintaxis existente ni formato binario. No afirmar optimalidad sin medir.

## Escritura
Una coordenada existente puede especificar la transformación como tratamiento + [t,v,i,x] si el contexto de datos está fijado; si el tratamiento ya está fijado basta [t,v,i,x]. Separar la creación de identidades nuevas (nombre como manifestación) y la primera constitución de un vector (referencia a declaración existente, no índice vectorial inventado). Definir de manera inequívoca el espacio de coordenadas de una solicitud: declaración frente a constitución, trayectoria privada frente a canónica. No enviar posiciones desnudas entre geometrías distintas. Mantener origen estable, bytes congelados, admisión MCVT y CAS. No cambiar T120 ni T101 automáticamente: primero probar el adaptador de frontera, luego estudiar el costo y semántica de un perfil posicional canónico.

## Decisión y siguiente prueba
No alterar RC.2. Validar una proyección posicional contra el mismo recorrido original, con tipos declarados en orden distinto del de constitución, campos constituidos en orden distinto del de declaración, identidad creada sin parámetros, vector con huecos, cero/false, equivalencia nominal/posicional, referencias conservadas por extensión, y JS/PHP. Después decidir gramática de escritura para primeras apariciones. Esta revisión inspeccionó código fuente, no ejecutó nuevas pruebas ni demostró la optimalidad de la propuesta.
