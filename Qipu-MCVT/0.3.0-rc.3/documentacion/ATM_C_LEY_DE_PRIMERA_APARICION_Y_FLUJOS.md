# ATM-C — Ley de primera aparición, referencia y método de trabajo
Claridad conceptual del proyecto, noviembre de 2026. Complemento de RC.3; no cambia código ni formatos.

## 1. Ley fundamental
Lo todavía no constituido se introduce mediante información suficiente; lo ya constituido se referencia mediante posiciones. La primera aparición admisible asigna la siguiente posición dentro de su ámbito. Las apariciones posteriores conservan esa posición. No es necesario enviar una coordenada futura para crear algo, ni preasignarla. Puede ser necesario referir las coordenadas de su contexto ya constituido (tabla, vector, autoridad). Los nombres que introducen identidades son manifestaciones irreducibles, no etiquetas redundantes. El nombre de un valor textual es distinto de un nombre de campo repetido para identificar un selector conocido.

## 2. Flujos de utilización
Conocer: elegir trayectoria/vista/corte → preguntar por primeras apariciones si faltan coordenadas → adquirir posición → preguntar por manifestación, vector, historia o composición → traducir la respuesta al formato externo deseado.
Constituir: elegir contexto y tratamiento → aportar únicamente la información nueva y referencias ya conocidas → autoridad evalúa → anexar acontecimiento reconocido → recorrido asigna posiciones → conocer/entregar coordenadas derivadas cuando se soliciten.
Transformar: contexto + tratamiento + coordenadas + manifestación/diferencial → plan y admisión → anexar → derivar actualidad. SET cambia la respuesta actual, no sobrescribe la historia. ADD/SUB necesitan valor anterior y dominio admisible.
Cooperar: posiciones no se transportan sin su geometría de interpretación. Una intención se conserva con origen estable; Q recibe, C admite, R reconoce. Las posiciones privadas no se interpretan como canónicas. Una solicitud provisional no anticipa la posición firme.

## 3. Ejemplo de representación mínima (conceptual, no formato binario vigente)
Con tratamiento constitutivo previamente determinado, introducir el tipo Producto solo requiere el nombre Producto como información nueva del tipo; la posición de tabla deriva. Para introducir SKU-A bajo tabla 0, basta [0,"SKU-A"] como argumentos del tratamiento de identidad. Para introducir Precio bajo tabla 0, [0,"Precio",dominio] si el dominio no está ya determinado por el tratamiento/contrato. La primera manifestación puede introducir el vector según el perfil; no se exige crear un registro auxiliar de metaestructura. Después de constituir t=0, v=0, i=0, una asignación usa [0,0,0,35000] en contexto SET. Si el contexto de tabla/vector está fijado pueden omitirse coordenadas ya determinadas. Si una escritura contiene varios efectos, la atomicidad depende de su tratamiento contractual, no de agrupar JSON.
No confundir tipo de entidad Producto (tabla al constituirse) e identidad particular SKU-A. El código histórico T13 tiene ámbitos diferentes; T13 ámbito 3 puede constituir tabla, identidad, vector y valor, mientras Comercio Vectorial separa algunos ámbitos. QIPU-META-1 de RC.3 exige DEF previo: declarar tipo no materializa tabla, ID crea tabla/identidad, SET crea vector permitido. No imponer el perfil declarativo como ley universal.

## 4. Auditoría concreta RC.3
En local/atm-coordinate.js, compile normaliza selectores conocidos a posiciones, y retiene nombres para primeras apariciones. Pero también genera legacy=[op,ev.table,ev.identity,ev.parameter,ev.value] para compatibilidad. ATMC.Local.stage llama a ATM.Local.stage(legacy,origin); ATM registra T120 con origin y event nominal. servidor/ATMCoordinate.php realiza la misma traducción. DurableNode.requestCoordinate conserva T101 con event nominal para cruce de frontera. Así, RC.3 satisface la ley en la interfaz de intención, no en la codificación canónica completa: una modificación de un valor existente todavía repite table, identity, parameter y operation por nombre. Estos nombres no son únicamente manifestaciones nuevas. El perfil usa además nombres de campos del envoltorio JSON. Las 104 pruebas anteriores validan equivalencia y persistencia de este formato, no su minimalidad. No afirmar que ya se eliminaron todos los nombres repetidos.
La diferencia no obliga a cambiar inmediatamente el núcleo: evaluar un perfil canónico posicional explícitamente versionado, con replay contra prefijo correcto, primeras apariciones mixtas, procedencia, CAS, reintentos idénticos y reconocimiento C/R. No traducir un registro posicional en otra geometría ni reinterpretar T120 histórico. Primero definir y comprobar semántica; después medir longitud, costo de resolución, almacenamiento de índices, memoria y tiempo.

## 5. Invariante matemático
Para cada ámbito de identidad, pos_n(x)=número de identidades distintas que tuvieron primera aparición admitida antes de x. Si x ya existe en un prefijo y se extiende de forma conservativa, pos_m(x)=pos_n(x) para m>=n. El conteo es por primeras apariciones de ese ámbito, no por cantidad de registros. El orden de constitución pertenece al recorrido. Una proyección de objeto reúne manifestaciones que comparten índice, no constituye un objeto adicional.
La economía de representación es condicionada por el conocimiento compartido. Si una posición ya determina un nombre no es necesario transmitir ambos; si el valor es nuevo y no está determinado debe transmitirse. Esto justifica una hipótesis de residuo mínimo, no una demostración de optimalidad global. Los índices son derivados reconstruibles y pueden acelerar preguntas sin cambiar autoridad.

## 6. Método de trabajo
Antes de escribir código: (a) formular la pregunta/intención y su universo; (b) identificar información nueva, referencias y contexto; (c) definir ley de constitución/recorrido y su rechazo; (d) comprobar conservación posicional, replay, origen e invariantes de autoridad; (e) separar proyecciones de persistencia; (f) medir alternativas con cargas concretas. No introducir un esquema, registro, traductor o endpoint independiente si no aporta información o capacidad necesaria. El traductor de entrada resuelve significado, el de salida proyecta; ninguno inventa autoridad o coordenadas.

Esta nota es revisión de código y clarificación de diseño, no nueva ejecución de pruebas ni cambio del perfil canónico.
